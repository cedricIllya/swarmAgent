# Runtime

`apps/agent-runtime` — один процесс Node на машине агента. Он принимает почту, держит свой Chromium и зовёт Hermes. Пока открыт браузер или идёт задача, машина не спит: код из письма вводится в ту же сессию.

Слушает `[::]:8787` — оба стека. Приватная сеть Fly только IPv6, на `0.0.0.0` control plane получал бы `ECONNREFUSED`. Всё, кроме `GET /health`, требует `Authorization: Bearer <RUNTIME_TOKEN>`.

## Сон

Автостоп прокси выключен: он усыплял бы машину лишь через несколько минут простоя и всё это время брал бы деньги за CPU и RAM. Runtime сам следит за простоем и просит suspend через 2 минуты. Будит не API `start`, а следующий запрос на `http://<app>.flycast:8787`: прокси держит соединение, пока машина не встанет. Старый адрес `.internal` прокси не видит, такие агенты по-прежнему поднимаются через `start`.

Через 2 минуты после последнего письма, чата или шага браузера, если нет задачи в статусе `running`/`queued` и нет открытой сессии, runtime просит `POST /api/runtime/suspend`. Ожидание одобрения сну не мешает. Пустой тик засыпает сразу. `IDLE_SUSPEND=off` или пустой `CONTROL_PLANE_URL` отключают сон. `IDLE_SUSPEND_MS` меняет паузу, по умолчанию 120000.

Control plane отвечает на suspend и только потом вызывает Fly `suspend`, чтобы процесс успел получить ответ. Опрос карточки раз в 5 секунд машину не будит: если она `suspended` или `stopped`, API отдаёт `asleep: true`. Первое открытие карточки передаёт `?wake=1` и будит ненадолго, чтобы показать журнал.

Диск 3 GB тарифицируется и во сне ($0.15 за гигабайт в месяц). Не тарифицируются CPU и RAM. Уже созданный volume Fly уменьшить нельзя.

## Контейнеры

Одна Machine, 1 shared CPU, 2 GB, volume `agent_data` на `/opt/data`, `restart: always`. Автостоп прокси выключен, сон делает API. Сервис на порту 8787 с `autostart` нужен только для Flycast.

1. **runtime** — этот процесс. В него же положены файлы `/bootstrap`. Healthcheck — exec `wget http://127.0.0.1:8787/health` (интервалы в секундах). HTTP-проверку контейнера Fly не использовать: с ней pilot не запускает ни один контейнер машины.
2. **hermes** — образ `HERMES_IMAGE`, команда `gateway run`. Стартует, когда runtime стал healthy, то есть конфиг уже лежит на диске. s6-overlay в образе Hermes хочет быть PID 1, поэтому это отдельный контейнер, а не второй процесс в том же.

Hermes слушает OpenAI-совместимый API на `127.0.0.1:8642`. Ключ — тот же runtime-токен. Runtime даёт ему задачи туда. Если API не отвечает, ответ собирается прямым вызовом OpenRouter без инструментов, и задача не теряется. Поля `api_server` в `.env` Hermes взяты по публичному контракту образа; при первом реальном запуске Hermes их стоит сверить с его документацией.

## Что делает процесс

Письмо приходит на `POST /email` и обрабатывается в фоне. Правила — в [почте](mail.md).

Чат карточки — несколько отдельных переписок. У каждой своя история в `chats/<id>/` и своя сессия Hermes: `threadId` задачи равен id чата. `POST /chat` без `chatId` заводит новый чат, с `chatId` пишет в существующий. Сообщение классифицируется: приглашение, ключ или задача. Приглашение идёт по лестнице MCP → API → браузер, ключ проверяется и пишется через `/report`.

## Приглашение в сервис

Порядок онбординга (`onboarding.ts`), всё до первого хода модели:

1. Сопоставить приглашение с каталогом по доменам ссылок, DKIM и подсказке классификатора.
2. Рецепта нет — поиск способа входа (ниже).
3. Принять приглашение и зарегистрироваться под почтой агента — всегда в браузере (`runtime/browser.ts`, `acceptInvite`). Через API или иным «программным» путём приглашение не принимается: такого пути в runtime нет, и подсказка с скиллом прямо говорят агенту его не предлагать. Одобрения владельца этот шаг не требует.
   - **Skyvern** (`browser/skyvern.ts`), если задан `SKYVERN_API_KEY`. Одна задача `POST /v1/run/tasks` с инструкцией: открыть ссылку, нажать «принять», выбрать вход по почте (не Google/SSO), самому ввести имя агента и пароль (его придумывает runtime) до отправки формы, затем дождаться кода. Задача запускается с `totp_identifier` = почта агента и `browser_session_id`. Пока ящик захвачен, входящее письмо целиком (тема и текст, до 6000 символов, без вырезанного кода) уходит в `POST /v1/credentials/totp` с тем же идентификатором; `task_id` добавляется, только если ждущая задача одна. Ответ в существующей переписке туда не попадает. Письмо, пришедшее раньше идентификатора, лежит в буфере около 15 минут и отдаётся на старте задачи. После отпускания ящика то же письмо разбирается обычным путём. Ошибка TOTP задачу не валит. В конце Skyvern возвращает `outcome` (`accepted`, `captcha`, `expired`, `needs_human`, `pending_approval`, `failed`), `password_set` и `final_url`; ролик по `recording_url` сохраняется как у обычной сессии.
   - **Свой Chromium** (`browser/invite.ts`), если Skyvern не настроен или вернул `failed`: сессия в профиле сервиса (`browser-profiles/<slug>`), цикл «определить состояние страницы → сделать шаг», код или magic link из письма через `wait-code`. Капча — `needs_human`, истёкшее приглашение — `failed`. Живого экрана нет.
   - **Регистрация, затем вход.** Пароль, который runtime придумал перед прогоном, — пароль регистрации, а не признак существующего аккаунта. Форму регистрации заполняют им. Если сервис после регистрации показывает обычный вход, вводят тот же адрес и тот же пароль. Сразу входить, минуя регистрацию, можно только когда аккаунт уже был: пароль сохранён прошлым прогоном или человек продолжает прерванный вход. «Забыли пароль» агент не открывает.
   - **Отказы.** «Неверный пароль» останавливает прогон сразу с барьером `password_rejected`. «Аккаунт с этим адресом уже есть» без сохранённого пароля — переход на вход кодом из письма. Придуманный пароль туда не вводится, со второго такого отказа нужен человек. Страница не разобралась — одна повторная попытка, после двух сбоев подряд прогон `failed`.
   - После входа runtime записывает доступ (`type=credential`: `accountEmail`, `accountName`, `password`; для своего браузера ещё `storageState.profile`), а если рецепта ещё нет — минимальный браузерный рецепт, чтобы было куда привязать доступ. Логин и пароль владелец видит в журнале задачи, в блоке «Доступы».
4. Итог всех шагов попадает в подсказку задачи: «Шаг 0 выполнен/не завершён», рецепт или находки, что делать дальше. Дальнейшая работа — лестница MCP → API → браузер; если дошло до браузера, агент открывает свой Chromium с `serviceSlug`: cookies после своего браузера уже в профиле, после Skyvern runtime переносит их туда по CDP перед закрытием сессии. Если перенос не удался — вход по сохранённому паролю.

Пока открыта сессия Skyvern или свой браузер ждёт код, `busyInBrowser` истинен и машину не усыпляют. Почту в Skyvern забирает только захват ящика на время задачи входа: письмо откладывается и после отпускания читается снова. Код, пришедший пока сессия своего браузера открыта, но ещё не вызвала `wait-code`, придерживается в сессии 10 минут — ближайший `wait-code` получит его сразу. В страницу Skyvern код не вставляется.

## Поиск сервиса, которого нет в каталоге

Если рецепта нет, runtime запускает поиск (`discovery/`):

1. Домен сервиса — по подсказке классификатора или самому частому корневому домену среди ссылок без рассылочного шума (sendgrid, mailgun и т.п.).
2. Официальный реестр MCP (`registry.modelcontextprotocol.io`): берутся только удалённые серверы, принадлежащие домену (обратный DNS в имени, `websiteUrl` или хост `remotes`).
3. Типовые адреса на домене: `mcp.<d>/mcp`, `<d>/mcp`, `<d>/api/mcp`, `api.<d>/mcp`, `mcp.<d>/sse`.
4. Каждый кандидат проверяется настоящим `initialize`: `200` с JSON-RPC — MCP без токена, `401/403` — MCP с bearer или OAuth (по `WWW-Authenticate`), остальное — не MCP.
5. Документация: один веб-поиск через OpenRouter (плагин `web`). Если поиск уже дал базовый URL API, страницу документации из цитат и где взять ключ, страницы не читаются. Иначе читается корень, который назвал поиск: `llms.txt` и `sitemap.xml` на этом хосте, затем не больше двух страниц (индекс и одна про API, ключ или MCP). Типовые `docs.<d>`, `developers.<d>` и `<d>/docs` запрашиваются только когда поиск ничего не назвал. Модель извлекает базовый URL API, заголовок авторизации, где взять ключ и адрес входа. MCP из документации проверяется так же. Если MCP уже ответил без токена, поиск документации не запускается.

Результат попадает в подсказку задачи. Подтверждённый MCP с домена сервиса записывается рецептом сразу (`applyReport`), и Hermes получает инструменты `mcp_<slug>_*` до хода модели; остальное — черновик рецепта, который агент проверяет и пишет через `/report`. Шаги поиска видны в журнале задачи как `tool`, вызовы модели — в `usage.jsonl` как `discover.search`, `discover.extract`, `web.search`. Старый общий `chat.jsonl` при старте переносится в чат «Общий». Письма и плановые проверки пишут в чат «Почта и расписание». На карточке агента чата нет: владелец пишет задачу в одно поле, а история, кнопки человека и доступы открываются в журнале этой задачи. Если задача ждёт одобрения, кнопки «Да» и «Нет» (или «Я доделал, продолжай») стоят в её журнале; решение и ответ после него остаются в истории той же задачи. У идущей задачи в шапке журнала есть «Остановить»: она обрывает ход Hermes, закрывает браузер (в том числе Skyvern) и снимает ожидания одобрения. Остановленную задачу можно «Повторить».

Ответ человеку ограничен его сервисами и публичным интернетом. Системная инструкция и скилл `swarm-worker` запрещают пересказывать устройство Swarm. Перед чатом, письмом, одобрением, итогом задачи и заметкой агента runtime вырезает локальные адреса, пути `/opt/data`, имена ключей и значения `Bearer`.

В каждую подсказку хода добавляется `runId` — без него `/browser/*`, `/approval` и `/report` не работают. После хода runtime смотрит журнал: если не было шагов `mcp`/`api`/`browser` (или записи доступа через `/report`) и ответ не «пусто / задач нет», делается один повтор; иначе задача `failed`. Ответ без Hermes (fallback OpenRouter) тоже `failed` — там нет инструментов.

Тик раз в `TICK_MINUTES` (по умолчанию 15) и по `POST /tick`. Новая почта тут не опрашивается. Тик забирает отложенные письма, если браузер свободен, и просит Hermes посмотреть задачи в сервисах, к которым у этого агента уже есть доступ. Нет таких сервисов — тик только разбирает отложенную почту.

Пока машина спит, её собственный таймер и cron Hermes стоят. Будит control plane: раз в 15 минут, если он сам не спит, и сразу после пробуждения. Агента без секретов сервисов он не поднимает.

Каждый вызов модели дописывает строку в `usage.jsonl`: задача, действие (`classify.email`, `hermes.turn`, `stagehand.llm`, …), источник, токены и `cost` из ответа OpenRouter. К ходу Hermes прикладываются `details` — шаги, записанные в журнал задачи за время этого хода (заметки агента через `/runs/:id/step`, браузер, письма, одобрения). В карточке вместо кода действия показываются именно они.

## Браузер

Сессия — headless Chromium на машине агента (`CHROME_PATH`, в образе `/usr/bin/chromium`). Если передан `serviceSlug`, профиль берётся из `browser-profiles/<slug>/`: cookies сервиса остаются между сессиями. Один профиль открыт только в одной сессии.

Stagehand думает моделью агента. Свой вызов модели runtime отправляет в OpenRouter и пишет стоимость в ту же задачу. Шаги `act`, `extract`, `observe`, переходы и полученный код пишутся в `actions.jsonl`. После перехода и после каждого действия runtime сохраняет jpeg кадра в `browser-sessions/<id>/shots/`. В чате и в журнале задачи эти кадры видны лентой. Живого экрана и ролика у своего браузера нет. Если вход остановился и нужен человек, карточка даёт ссылку на страницу сервиса, где агент остановился: её открывают у себя, доделывают шаг и нажимают «Я доделал».

`POST /browser/wait-code` ждёт, пока почтовая дверь передаст код или ссылку. Пока ожидание висит, `busyInBrowser` истинен и чужая почта откладывается.

Skyvern — только онбординг: приглашение (`/invite/accept`), `signup` и `login` (`POST /skyvern/login`). Он обходит капчи. Каждая задача запускается с `totp_identifier` = почта агента, и коды из писем runtime передаёт в неё сам. Данные формы (`credentials`) попадают в текст инструкции. Ролик по `recording_url` скачивается в `browser-sessions/<id>/video.mp4`. После успешного входа runtime по CDP снимает cookies/localStorage сессии и засевает их в `browser-profiles/<slug>/`, чтобы задачи внутри сервиса шли в своём Chromium уже вошедшими. Если Skyvern не настроен или не довёл вход, тот же цикл идёт в своём Chromium. Задачи внутри сервиса Skyvern не выполняет.

| GET | `/browser-sessions/:id/video` | MP4. |

| Метод | Путь | Зачем |
| --- | --- | --- |

| POST | `/approval` | Спросить человека перед изменением. |

| POST | `/discover` | Поиск способа входа в сервис вне каталога: `runId`, `service`, `domain`, `links`. Отдаёт известный рецепт или результат поиска с черновиком рецепта. |

## Обратно на control plane

`CONTROL_PLANE_URL` пустой — отправка почты и отчёты пропускаются, в лог пишется предупреждение. Иначе:

- `POST /api/runtime/send-email`
- `POST /api/runtime/report`
- `POST /api/runtime/suspend`

Оба с bearer runtime-токена и `X-Agent-Id`.
