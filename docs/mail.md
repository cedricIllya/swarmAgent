# Почта

Один catch-all домен Mailgun и один вебхук. Отдельного ящика у провайдера на агента нет. Кому письмо, решает приложение по адресу получателя.

## Адрес агента

Локальная часть индивидуальна для владельца: логин владельца, точка, имя агента. Логин — часть его email до `@` без плюс-тега, в нижнем регистре, не длиннее 32 символов: `John.Doe+work@corp.com` → `john.doe`. Имя агента транслитерируется, слова идут через точку, внутри слова всё, что не буква и не цифра, становится дефисом. `cedric@gmail.com` + `Владимир Ленин` → `cedric.vladimir.lenin`. Пустое имя → `agent`.

Имя агента обрезается так, чтобы вся локальная часть вместе с возможным числовым суффиксом уложилась в 64 символа. Если адрес всё же занят (тот же владелец и то же имя), дописывается число без лишней точки: `cedric.vladimir.lenin2`. Администратор может задать локальную часть сам: только `A-Za-z0-9._-`, не длиннее 64 символов; к ней логин не добавляется.

Плюс-адрес принадлежит голому: `name+tag@domain` ищется как `name@domain`. Регистр домена и локальной части не важен. Домен — `AGENTS_DOMAIN`, либо свой `agents_domain` тенанта, если это receiving-домен того же Mailgun.

## Приём

`POST /webhooks/email` — единственный URL, который видит Mailgun. Ответ 200 уходит сразу, доставка на машину агента идёт после ответа. Два формата тела сводятся к одной структуре `InboundEmail`.

**Form-urlencoded, Mailgun Routes.** Поля `recipient`/`to`, `sender`/`from`, `subject`, `body-plain`/`stripped-text`, `body-html`/`stripped-html`, `message-headers` (JSON-список пар). Вердикты `X-Mailgun-Spf` и `X-Mailgun-Dkim-Check-Result`.

**JSON, как у Postmark.** `From`, `To`/`OriginalRecipient`, `Subject`, `TextBody`, `HtmlBody`, `Headers`, `StrippedTextReply`, `MessageID`.

Из HTML достаются текст и ссылки, скрипты и стили выкидываются. `replyText` — тело без цитаты. `references` — не больше 20 id. `dkimDomains` — домены из `d=` каждой `DKIM-Signature`. Заголовки хранятся в нижнем регистре, первое значение.

### Двери вебхука

Подпись Mailgun: HMAC-SHA256 от `timestamp + token` ключом `MAILGUN_SIGNING_KEY`, hex. Окно — 5 минут. Плохая или старая подпись → 403.

| Что задано | Form | JSON |
| --- | --- | --- |
| Только signing key | Нужна подпись Mailgun | 403 |
| Только `INBOUND_WEBHOOK_TOKEN` | Нужен токен | Нужен токен |
| Оба | Токен и подпись | Токен |
| Ничего | Принимается, в лог пишется предупреждение | То же |

Токен читается из `X-Webhook-Token` или `Authorization: Bearer` и сравнивается побайтово.

Дальше адрес получателя разбирается, плюс-тег снимается, агент ищется в `agents`. Агента нет — строка в лог, письмо не обрабатывается и задача не создаётся. Агент не в статусе `running` или runtime не ответил — то же, в лог.

## Три двери на машине агента

Порядок фиксированный.

1. **Ответ в ветке.** `In-Reply-To` или `References` совпали с Message-ID письма, которое агент сам отправил. Всё `replyText` после нижнего регистра и снятия пунктуации сравнивается со словами. `да`, `yes`, `ок`, `ok`, `okay` и короткие синонимы подтверждают ровно тот вопрос, который ждал ответа. `нет`, `no`, `отмена`, `stop` отменяют. Текст длиннее — новая задача в той же ветке. Это не отдаётся браузеру и не запускает онбординг. Слова читает код, не модель.
2. **Агент ждёт код в браузере.** Письмо откладывается и будет прочитано снова, когда браузер освободится. Отдельные 4–8 цифр сразу уходят в ждущую сессию. Ссылка для входа — только если модель назвала письмо `verification` и в теле есть URL. Письмо от владельца этой дверью не перехватывается: оно читается как почта.
3. **Новое письмо.** Модель относит его к `invite`, `task`, `verification`, `notification` или `other`. Приглашение становится задачей онбординга по лестнице MCP → API → браузер. Если модель ответила 429, пустым телом или не ответила вовсе, а в письме есть ссылка приглашения (`invite`, `join`, `register?invite`) или тема «приглашение» — онбординг всё равно начинается. Такая же ссылка, вставленная в чат почти без другого текста, тоже приглашение, даже если модель назвала её задачей. Временная ошибка без ссылки откладывает письмо и повторяет разбор ещё два раза. Просьба — задачей, ответ уходит в ту же ветку. Уведомление и код без открытого браузера фиксируются и действий не вызывают.

Исходящие письма шлёт control plane через Mailgun API с адреса агента. Message-ID сохраняется в `sent.json`, чтобы узнать ответ в ветке.

Автономный флаг не отменяет двери. Он только убирает вопрос «можно ли менять»: runtime сразу считает изменение одобренным.

## Настройка Mailgun

`pnpm mailgun` читает `MAILGUN_API_KEY`, `MAILGUN_REGION` (`us` или `eu`), `AGENTS_DOMAIN`, `WEBHOOK_URL`. Секреты не печатает. Повторный запуск ничего не дублирует.

| Команда | Действие |
| --- | --- |
| `status` | Домен и route. Печатает DNS, ничего не меняет. |
| `domain` | Создаёт receiving-домен, если его нет. `spam_action=tag`, не `block`: коды и инвайты не выкидываются. |
| `verify` | Просит Mailgun перепроверить DNS. |
| `route` | `match_recipient(".*@домен")` → `forward(WEBHOOK_URL)` → `stop()`. |

MX `mxa.mailgun.org` и `mxb.mailgun.org`, SPF и DKIM ставятся у регистратора вручную. Скрипт DNS не меняет.
